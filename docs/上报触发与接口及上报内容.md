# 安装量 / 活跃度上报 — 触发机制 · 接口 · 上报内容

> **适用版本**：**v1.29.0 起**（v1.30.x 沿用；**v1.35.9 起载荷收敛为单字段 `upapi`**；**v1.35.11 起 `upapi` 只由 `device_uuid` 是否变化决定**，见 §2.1 / §2.2）。
> **实现唯一来源**：`server/telemetry.ts`（后端全部逻辑）；展示层 `src/components/ActivityPanel.tsx`；请求封装 `src/api.ts`。
> **实测样例载荷**：`docs/上报.json`。
> **本工程只做「上报端」**——中心统计服务（接收 / 去重 / 清洗 / 看板）由**独立后端**实现，不在本仓库内。

---

## 0. 速览

| 项 | 值 |
|---|---|
| 上报类型 | **单字段 `upapi`** —— v1.35.9 起取值 **`install`（安装 / 重装）/ `heartbeat`（纯心跳）**，取代原先「常量 `event` + 布尔 `install`」两个字段；★ **v1.35.11 起只由 `device_uuid` 是否变化决定**（变了 ⇒ `install`，没变 ⇒ `heartbeat`；开关切换恒 `install`），故 **`install` 次数 ≈ 去重设备数**（§2.1） |
| 上报端点 | `POST https://yanzi-api.ziruxue.top/api/yanzi-docker/event` |
| 鉴权头 | `X-Telemetry-Key: <deviceId>`（＝本机硬件指纹，**不用随机 UUID**） |
| 上报内容 | **仅本机设备信息**（硬件指纹 + 硬件明细 + 系统 + 应用版本）；**不含容器 / 镜像 / 堆栈等业务数据，也不含账号信息** |
| 触发时机 | 安装·重装 / 进程启动·重启（延迟 30 秒）/ 每 12 小时 / 失败 10 分钟后重试 / 上传开关切换瞬间 |
| 总开关 | 系统设置 → 本机设备 → **「上传安装数量统计」**（`settings.telemetry.enabled`，**默认开启**） |
| 容错铁律 | **任何失败都不得影响主业务**，只写运行态 `lastError` |
| 超时 | 单次请求 **10 秒** |

## 1. 文件落点

| 文件 | 路径（生产） | 写入策略 | 内容 |
|---|---|---|---|
| **标识文件** | `<安装目录>/config/device.info` | **只在创建 / 重建时写一次**，其余时刻纯只读 | `deviceId`（硬件指纹）、`createdAt`（≈安装时间）、`virtualized`、`hardware`（安装时 6 维快照） |
| **运行态文件** | `<安装目录>/config/telemetry-state.json` | 每次上报后写 | `installReported` / **`lastDeviceId`**（v1.35.11 起，上次成功上报的 `device_uuid`）/ `lastReportAt` / `lastRebuildAt` / `lastError`（v1.35.9 起 `lastActiveAt` 已合并进 `lastReportAt`） |
| **上传开关** | `<安装目录>/config/settings.json` 的 `telemetry.enabled` | 用户在设置页保存 | 布尔，缺省视为 `true` |

- 目录解析见 `server/paths.ts`：环境变量 `CONFIG_DIR` > 生产默认 `<cwd>/config` > 开发默认 `<项目根>/config`。其中 `<cwd>` 对 SEA 单文件即**安装目录**（`server/config.ts` 里 `APP_DIR = process.cwd()`）。
- 默认安装目录 `/opt/docker-manager-yanzi`，故生产路径通常是 `/opt/docker-manager-yanzi/config/device.info`。
- **标识文件与运行态文件刻意分离**：reasons 见 §7。

## 2. 触发时机

### 2.1 完整时机表

**总规则（v1.35.11 起）**：`upapi: "install"` ⟺ 本次 `device_uuid` **≠** 上次**成功**上报的 `device_uuid`（含「从未成功上报过」）；其余一律 `"heartbeat"`。**唯一例外**：上传开关切换恒 `"install"`（用户显式操作）。

| # | 时机 | 本次上报（`upapi` 取值） | 是否受周期约束 | 代码入口 |
|---|---|---|---|---|
| 1 | **首次安装**（标识文件不存在 ⇒ 从未成功上报过） | `"install"` | 否 | `startTelemetryHeartbeat()` → 延迟 30s → `reportOnce("startup")` |
| 2 | **重装 / 更新后启动**，标识文件 `btime ≠ mtime`（被改写）⇒ 重建标识 | `device_uuid` **变了** ⇒ `"install"`；**没变** ⇒ `"heartbeat"` | 是（但 24h 限流**不再影响取值**，见 §7.3） | `getDeviceInfo()` 重建标识文件 |
| 3 | **进程启动 / 重启**（systemd start / restart） | `device_uuid` 未变 ⇒ **恒 `"heartbeat"`** | **否**（强制发送，忽略 12h 判断） | `startTelemetryHeartbeat()` → 延迟 30s → `reportOnce("startup")` |
| 4 | **每 12 小时** | **恒 `"heartbeat"`**（纯心跳） | 是 | `scheduleNext(REPORT_INTERVAL_MS, "periodic")` |
| 5 | **上报失败后 10 分钟** | **恒 `"heartbeat"`** | 否（强制） | `scheduleNext(RETRY_INTERVAL_MS, "retry")` |
| 6 | **上传开关 开↔关 保存瞬间** | **恒 `"install"`**（例外），只发 1 条 | 否 | `PUT /api/settings` → `reportOnToggle()` |
| 7 | **手动触发**（后端接口，前端未接线，见 §4.2） | **恒 `"heartbeat"`**（ID 未变时） | 否 | `POST /api/telemetry/report` → `reportOnce("manual")` |
| 8 | （副作用）**打开「本机设备」设置页** | 只做校验，**不发请求** | — | `GET /api/telemetry/status` → `getDeviceInfo()` |

> ⚠️ 第 8 条说明：`getTelemetryStatus()` 内部会调 `getDeviceInfo()`，也就是**读一次标识文件完整性**。若此刻恰好发现文件被改写，会**顺手重建**标识文件（真正的上报仍由下一次 `reportOnce` 发出）。**只看设置页并不会直接产生网络请求。**
>
> ★★ **v1.35.11 起 `upapi` 只由 `device_uuid` 是否变化决定**，与触发源解耦 —— 于是 **`install` 次数 ≈ 去重后的设备数**，不再被「重启 / 周期 / 重试」的次数放大。要点：
> - **每次进程启动 / systemd restart 不再报 `install`**（ID 没变 ⇒ `heartbeat`）。这是 v1.35.10「启动即 install」的反转，按用户要求落地。
> - 标识文件被反复改写但硬件没变（ID 不变）时也不会刷高安装量 —— 旧版靠 24 小时限流达成的保护，现在由身份判据天然覆盖。
> - ⚠️ 从 ≤ v1.35.10 升级上来时，运行态没有 `lastDeviceId` ⇒ **无法证明「未变」⇒ 保守补发一次 `install`**，写入后即回归正常（一次性）。
> - 溯源：v1.35.9 之前用 `needInstall = reportInstall || !installReported` 推导，端点长期不可达时 `installReported` 永不上位 ⇒ **所有**触发都退化成 `install`；v1.35.10 曾改为「按触发源」（`startup` ⇒ install），v1.35.11 再改为「按 `device_uuid`」即本表。

### 2.2 事件选择规则（`reportOnce`，代码级）

```ts
// 触发源：startup（启动首报）/ periodic（12h）/ retry（失败后 10min）/ manual（页面「立即上报」）
// v1.35.11 起：trigger 只决定「要不要强制发」，不再决定 upapi 取值
export type ReportTrigger = "startup" | "periodic" | "retry" | "manual";

const { info } = getDeviceInfo();              // 顺带做标识文件自愈
const state = readState();

// ★ 唯一判据：device_uuid 变了（或从未成功上报过）⇒ install
const upapi = resolveUpapi(state, info.deviceId);   // !installReported || lastDeviceId !== deviceId ? install : heartbeat
const needInstall = upapi === "install";
const force = trigger !== "periodic";               // 启动 / 重试 / 手动 ⇒ 强制发送
const shouldSend = needInstall || force || dueForPeriodic(state);
if (!shouldSend) return { sent: [], upapi: null };  // 都不需要 → 零网络请求

// 发出（恒 1 条）：buildPayload(info, collectHw, enabled, upapi)
// 成功 ⇒ writeState({ installReported: true, lastDeviceId: info.deviceId, lastReportAt: now })
```

要点：

- **一次 `reportOnce` 恒定只发 1 条请求**，载荷里只有一个类型字段 `upapi`（v1.35.9 起取代「常量 `event` + 布尔 `install`」两个字段 —— 一个字段讲一件事）。
- ★ **v1.35.11 起 `upapi` 由 `device_uuid` 是否变化决定**（`resolveUpapi(state, deviceId)`），**触发源不参与**：
  | 情形 | `upapi` |
  | --- | --- |
  | 从未成功上报过（＝首次安装） | `install` |
  | 当前 `device_uuid` ≠ 上次成功上报的 `device_uuid`（重装 / tampered 后身份变了） | `install` |
  | `device_uuid` 未变（**含每次进程启动 / systemd restart**）、12h 周期、失败重试、手动上报 | `heartbeat` |
  | 上传开关切换（`reportOnToggle`） | `install`（恒，**用户显式操作例外**） |
- `lastDeviceId` 在**每次成功上报**（含开关切换）时写入 ⇒ 下次只有「ID 变了」才会再报 `install`，不会因缺字段反复补发。
- `lastDeviceId` 缺失（从 ≤ v1.35.10 升级上来）⇒ 保守补发一次 `install`（一次性）。
- `needInstall` 现在**只由 `upapi` 推出**，用于决定「要不要发」（install 必发），不再反向影响取值。
- 标识文件重建的 24 小时限流（`reportInstall`）**不再影响 `upapi`**：仍写 `lastRebuildAt`、仍打告警日志，仅供观测（§7.3）。
- `dueForPeriodic`：`lastReportAt` 缺失／不可解析 → 视为到期；否则判 `now - lastReportAt >= 12h - 60s`（60 秒宽限，见 §2.3）。
- **每次上报成功只刷新一个 `lastReportAt`**（v1.35.9 起把恒同值的 `lastActiveAt` 合并进来；远端据此判在线），所以安装后不会紧接着再补发一条心跳。
- 不需要发时**直接返回、零网络请求**。

### 2.3 时间常量表

| 常量 | 值 | 作用 |
|---|---|---|
| `FIRST_REPORT_DELAY_MS` | **30 秒** | 启动后延迟首报，避开开机阶段网络未就绪与启动资源争抢 |
| `REPORT_INTERVAL_MS` | **12 小时** | 心跳周期 |
| `DUE_SLACK_MS` | **60 秒** | 周期判定宽限：定时器可能比整点早几十毫秒，避免因此空转一轮 |
| `RETRY_INTERVAL_MS` | **10 分钟** | 失败重试间隔（仅可重试错误） |
| `REQUEST_TIMEOUT_MS` | **10 秒** | 单次 HTTP 超时（`AbortSignal.timeout`） |
| `REBUILD_MIN_INTERVAL_MS` | **24 小时** | 标识文件重建限流窗口。★ v1.35.11 起**不再影响 `upapi`**（改由 `device_uuid` 判据决定），仅保留「写 `lastRebuildAt` + 打告警日志」供观测 |
| `MTIME_TOLERANCE_MS` | **2 秒** | `btime` 与 `mtime` 比较容差（创建＝create + write 两个动作，可能跨秒） |

### 2.4 调度链（定时器状态机）

```
startTelemetryHeartbeat()               // 幂等：started 标记，重复调用直接 return
        │
        └─ scheduleNext(30s, "startup")
                 │
                 ▼  (setTimeout, 已 unref —— 不阻止进程退出)
            reportOnce(trigger)         // upapi 由 device_uuid 判据决定（与 trigger 无关）
                 │
                 ├─ r.error && !r.fatal   → scheduleNext(10 分钟, "retry")
                 └─ 否则                  → scheduleNext(12 小时, "periodic")
```

- 定时器链**单条、自递归**，`scheduleNext` 每次先 `clearTimeout(timer)`；`trigger` **只决定是否强制发送**（`periodic` 之外都强制），**不再决定 `upapi`**。
- `nextAttemptAt`（模块级）＝下一次计划时间，通过 `GET /api/telemetry/status` 的 `nextReportAt` 暴露。
- **401 / 403 不进 10 分钟重试环**：判为鉴权失败（`fatal`），直接退回 12 小时周期，避免密钥错误时持续轰击远端。
- ✅ **关闭上传开关后的行为**：`reportOnce` 立刻返回 `{ sent: [], upapi: null, error: "上传已关闭", fatal: true }`（无网络请求）。★ **v1.35.9 起该返回值带 `fatal: true`**，调度器据此不再走 10 分钟重试、直接退回 12 小时周期 —— 修掉了 v1.32.0~v1.35.8 那个「关开关后每 10 分钟空转」的既有缺陷。

## 3. 上传开关

### 3.1 存储与默认值

| 项 | 说明 |
|---|---|
| 位置 | `settings.json` → `telemetry.enabled` |
| 默认 | **`true`（开启）**；`server/settings.ts` 里 `DEFAULT_SETTINGS.telemetry = { enabled: true }` |
| 旧配置升级 | 二级合并 `{ ...DEFAULT, ...parsed.telemetry }` ⇒ 老 `settings.json` 无 `telemetry` 段时自动继承「开启」，不报错 |
| 读取时机 | `readConfig()` **每次上报前实时读盘**（`getSettings()` 无缓存）⇒ **切换后无需重启、立即生效** |
| 前端归属 | `src/pages/Settings.tsx` 是**唯一写入方**（`update("telemetry","enabled",val)`），改动后需点右下角 **APPLY** 保存 |
| 类型 | 前端 `src/types.ts` 的 `TelemetryConfig { enabled: boolean }` |

### 3.2 关闭后的行为

- `reportOnce()` 第一行即判 `if (!cfg.enabled) return { sent: [], upapi: null, error: "上传已关闭", fatal: true }` ⇒ **零网络请求**，且调度器**不再 10 分钟重试**（见 §2.4 末注）。
- 本机设备标识卡片仍可正常查看（`GET /api/telemetry/status` 是本地接口，不走远端）。
- 定时器不会因此停止，但会退回 12 小时周期（v1.35.9 起；此前是每 10 分钟空转，见 §2.4 末注）。

### 3.3 开关切换瞬间的例外（重要）

`PUT /api/settings` 会先读旧值、再存新值，比较前后 `telemetry.enabled`：

```ts
const prevEnabled = ...prev?.telemetry.enabled ?? true;
const settings = saveSettings(req.body);
...
const nextEnabled = ...settings?.telemetry.enabled ?? true;
if (nextEnabled !== prevEnabled) {
  void reportOnToggle(nextEnabled).catch(() => {});   // 不阻塞响应
}
```

`reportOnToggle(enabled)` 的设计：

- **开启或关闭都发**，且**只发 1 条**（忽略 12 小时周期）；`upapi` **恒为 `"install"`** —— 这是 `device_uuid` 判据的**唯一例外**（按用户要求保留）：开关切换属**用户显式操作**，服务端可另凭载荷 `uploadEnabled` 字段识别真正的 opt-in 变化。
- 关闭方向：`reportOnce` 会被「上传已关闭」守卫拦下，因此这里**强制 `{ ...readConfig(), enabled: true }` 绕过守卫**，仍把最新开关状态透给远端。
- 载荷里的 **`uploadEnabled` 字段＝本次开关的「新值」**，使服务端能记录本机最新 opt-in 状态。
- 失败只写 `lastError`，不抛异常；成功则置 `installReported=true`、写入 `lastDeviceId`、刷新 `lastReportAt`（写 `lastDeviceId` 是为了避免下一次启动因「读不到上次 ID」而多补一条 `install`）。

> **语义**：这是「用户主动表达意愿」的一次性回执，**不是周期上报**。日常关闭状态下，除这次切换回执外不会再有周期请求。

## 4. 接口

### 4.1 对远端：上报接口（App → 中心服务）

| 项 | 值 |
|---|---|
| 方法 / 路径 | `POST {endpoint}/api/yanzi-docker/event` |
| `endpoint` 默认 | `https://yanzi-api.ziruxue.top` |
| 覆盖方式 | 环境变量 **`TELEMETRY_ENDPOINT`**（便于自建 / 联调） |
| 请求头 | `Content-Type: application/json`<br>`X-Telemetry-Key: <deviceId>`（＝硬件指纹，同时充当鉴权与统计主键） |
| 请求体 | JSON，字段见 §5 |
| 超时 | 10 秒（`AbortSignal.timeout(REQUEST_TIMEOUT_MS)`） |
| 成功判据 | HTTP `2xx` |
| 失败分类 | `401` / `403` → `fatal=true`（不密集重试）<br>其他非 2xx / 网络异常 / 超时 → `fatal=false`（10 分钟后重试） |
| 响应体 | **不解析**——只按状态码判定成功与否 |

`sendReport` 的行为（唯一出口，恒定只发 1 条）：

```ts
const res = await fetch(`${cfg.endpoint}${TELEMETRY_PATH}`, {
  method: "POST",
  headers: { "Content-Type": "application/json", "X-Telemetry-Key": info.deviceId },
  body: JSON.stringify(buildPayload(info, cfg.collectHwFingerprint, uploadEnabled, upapi)),
  signal: AbortSignal.timeout(10_000),
});
if (!res.ok) return { ok: false, error: `HTTP ${res.status}`, fatal: res.status === 401 || res.status === 403 };
return { ok: true };
```

### 4.2 本机：App 自身暴露的接口（前端 → App 后端）

全部挂在 `/api` 之下，**受登录鉴权守卫**（`server/index.ts:379` 的 `app.use("/api", ...)`，仅 `/api/auth/*` 免鉴权）⇒ 需带会话 Cookie。

| 方法 | 路径 | 说明 | 返回 |
|---|---|---|---|
| `GET` | `/api/telemetry/status` | 本机设备标识与上报状态 | `{ success, data: TelemetryStatus }` |
| `POST` | `/api/telemetry/report` | 立即上报一次（`reportOnce("manual")`，强制发送、忽略 12h 周期，`upapi` = `heartbeat`） | `{ success, data: { sent, upapi, error?, fatal?, status } }` |
| `GET` | `/api/settings` | 读设置（含 `telemetry.enabled`） | `{ success, data: Settings }` |
| `PUT` | `/api/settings` | 存设置；**若 `telemetry.enabled` 发生变化 → 异步触发 `reportOnToggle`** | `{ success, data: Settings }` |

> **⛔ `/api/telemetry/stats` 已在 v1.29.0 删除**（死代码，前端从未接线），现返回 404。

**已知接线状态（避免踩「UI 未必接线」的坑）**：

- `GET /api/telemetry/status` —— **已接线**，由 `src/api.ts` 的 `fetchTelemetryStatus()` 供 `ActivityPanel` 使用。
- `PUT /api/settings` 的开关联动 —— **已接线**，由设置页保存触发。
- `POST /api/telemetry/report` —— **⛔ 前端未接线**。`src/api.ts` 里 `reportTelemetryNow()` 已定义，但**全项目无任何组件调用它**（`ActivityPanel` 里没有「立即上报」按钮）。该接口目前**仅供后端 / 联调 / 脚本使用**（`curl` 或 `POST` 调用即可触发一次强制上报）。若将来要在 UI 上开「立即上报」，直接用已封装好的 `reportTelemetryNow()` 即可。

`TelemetryStatus` 字段（`GET /api/telemetry/status` 的 `data`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `deviceId` | string | 设备标识（硬件指纹 6 维哈希，统计主键） |
| `virtualized` | boolean | 是否虚拟化 / 容器环境 |

## 5. 上报内容（载荷字段字典）

`buildPayload(info, collectHw, uploadEnabled, upapi)` 产出 **15 个顶层字段**（v1.35.9 起把「常量 `event: "report"` + 布尔 `install`」两个冗余字段合并为单字段 `upapi`，同时删掉与 `device_uuid` 恒同值的 `hw_fingerprint`；v1.32.0~v1.35.8 为 **17** 个 ⇒ `17 − 1（hw_fingerprint） − 2（event + install） + 1（upapi） = 15`）。`collectHw` 目前恒为 `true`（`readConfig()` 里硬编码），即 `hardware` / `details` **始终携带**。

### 5.1 顶层字段

| # | 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|---|
| 1 | `device_uuid` | string | `info.deviceId` | **统计主键**＝本机硬件指纹（6 维 sha256） |
| 2 | `upapi` | `"install"` \| `"heartbeat"` | `resolveUpapi(state, deviceId)` | **上报类型（单字段，v1.35.9 起）**：`"install"` → 服务端覆盖设备快照 / 刷新安装时间；`"heartbeat"` → 纯心跳。信息量与旧的 `event` + `install` 严格等价。★ v1.35.11 起**由 `device_uuid` 是否变化决定**（变了或从未上报过 → `install`；没变 → `heartbeat`；开关切换恒 `install`），触发源不再参与 |
| 3 | `ts` | string | 发送时刻 | 上报时间（ISO 8601，UTC） |
| 4 | `uploadEnabled` | boolean | 开关新值 | 上传开关**当前状态**，供服务端记录最新 opt-in |
| 5 | `installedAt` | string | `info.createdAt` | **安装时间**（标识文件创建时间；重装 / 重建后为新的时间） |
| 6 | `app` | string | 常量 | `"docker-manager-yanzi"` |
| 7 | `appVersion` | string | `__APP_VERSION__` | 应用版本（构建时注入，如 `1.35.9`） |
| 8 | `os` | string | 常量 | `"linux"`（SEA 交付形态固定） |
| 9 | `osVersion` | string | `/etc/os-release` + `os.type()/release()` | 形如 `Linux 6.8.0 (Ubuntu 24.04.1 LTS)` |
| 10 | `arch` | string | `process.arch` | `x64` |
| 11 | `channel` | string | 常量 | `"sea-linux-x64"` |
| 12 | `virtualized` | boolean | 指纹采集 | 是否虚拟化 / 容器 |
| 13 | `deviceFile` | string | `DEVICE_FILE` | 标识文件路径（对应卡片「标识文件」） |
| 14 | `hardware` | object \| null | 安装时快照 | 6 维设备标识，见 §5.2 |
| 15 | `details` | object \| null | 实时采集 | 富硬件明细，见 §5.3 |

> ⚠️ **注意 `hardware` 与 `details` 的时点差异**：`hardware` 取自**标识文件里的安装时快照**（不刷新，可与 `deviceId` 复算校验）；`details` 是**上报当刻实时采集**的（换硬盘 / 加内存后 `details` 会变，`hardware` 不变）。

### 5.2 `hardware` — 6 维设备标识（安装时快照）

| 字段 | 含义 | 采集来源 |
|---|---|---|
| `system` | 系统 | `/etc/os-release` 的 `PRETTY_NAME` + `os.type()/release()` |
| `cpu` | CPU 标识 | `dmidecode -s processor-serial`，兜底 `dmidecode -t 4` 的 `ID:` |
| `gpu` | GPU 标识 | sysfs `/sys/bus/pci/devices/*`（class `0x03xx`）+ `pci.ids` 解析，兜底 `lspci -nn` → `nvidia-smi` |
| `memory` | 内存标识 | 总容量 GB 为主（`os.totalmem()`），`dmidecode -t memory` 序列号兜底（全 0 归零） |
| `diskUid` | 硬盘序列号 | `lsblk -d -n -o SERIAL`，跳过 `loop/ram/sr/zram`；兜底扫 `/sys/block/*/serial` |
| `boardSerial` | 主板序列号 | `/sys/class/dmi/id/board_serial` → `product_uuid` → `dmidecode -s baseboard-serial-number` |

### 5.3 `details` — 富硬件明细（与「本机设备」卡片逐项对应）

| 分组 | 字段 | 含义 | 采集来源 |
|---|---|---|---|
| `cpu` | `model` | CPU 型号 | `/proc/cpuinfo` 的 `model name` |
| | `cores` | 物理核数 | `lscpu` 的 `Core(s) per socket × Socket(s)`，兜底 `/proc/cpuinfo` 的 `cpu cores` |
| | `threads` | 逻辑线程数 | `nproc` |
| | `freqGHz` | 最高频率（GHz，2 位小数） | `lscpu` 的 `CPU max MHz`，兜底当前 `cpu MHz` |
| `gpu` | `model` | GPU 型号 | 同 `hardware.gpu` |
| | `memory` | 显存 | `nvidia-smi --query-gpu=memory.total` |
| `memory` | `model` | 内存型号（Part Number） | `dmidecode -t memory`，过滤 `Not/Unknown/NO DIMM/None` |
| | `sizeGB` | 总容量（GB，四舍五入） | `os.totalmem()` |
| `disk` | `serial` | 首个物理盘序列号 | 同 `hardware.diskUid` |
| | `model` | 硬盘型号 | `lsblk -d -n -o MODEL` |
| | `size` | 硬盘容量 | `lsblk -d -n -o SIZE` |
| `dmi` | `boardName` | 主板型号 | `/run/docker-manager-yanzi/dmi-board_name` → `/sys/class/dmi/id/board_name` |
| | `productSerial` | 产品序列号 | 同上（`product_serial`） |
| | `productUuid` | 系统 UUID | 同上（`product_uuid`） |

> 📌 **DMI 字段为什么要先读 `/run/docker-manager-yanzi/dmi-*`**：内核把 `product_serial` / `product_uuid` 的 sysfs 权限设为 `0400`（仅 root 可读），而服务以非 root 用户 `docker-manager-yanzi` 运行。`install.sh` 安装的 systemd 单元里带了一条 root 镜像动作，把这三个字段复制到世界可读的 `/run/...` 下。**OTA 不更新单元文件** ⇒ 老部署可能读不到，此时卡片显示「—」并在 hover 提示里给出重装命令。
>
> 📌 **`collectDmiIds()` 只服务展示，不参与指纹**；`collectBoardId()` 保持原样以确保指纹稳定。

## 6. 统计主键（`deviceId`）生成规则

### 6.1 6 维与哈希

```ts
const raw = [system, cpu, gpu, memory, disk, board].join("|");
const fingerprint = crypto.createHash("sha256").update(raw).digest("hex");  // 64 位十六进制
```

**不使用随机 UUID**——这样「同一台机器重装系统 / 重装应用」仍归为同一设备，且服务端可复算校验（`hardware` 快照与 `deviceId` 同源）。

### 6.2 虚拟化归零（重要设计）

**检测到虚拟化 / 容器时，6 维全部替换为字面量 `"0"`** 后再哈希：

```ts
const virtualized = detectVirtualization();
const system = virtualized ? "0" : collectOsVersion();
// …cpu / gpu / memory / disk / board 同理
```

检测手段（`detectVirtualization()`，命中任一即真）：`/.dockerenv` 存在、`/proc/1/cgroup` 含 `docker|kubepods|containerd|lxc`、`/proc/cpuinfo` 含 `hypervisor`、`/sys/class/dmi/id/product_name` 匹配 `VMware|VirtualBox|KVM|QEMU|Hyper-V|Xen|innotek|Parallels`、`systemd-detect-virt` 返回非 `none`。

**动机**：虚拟机 / 容器的硬件信息高度同质（尤其云主机），不做归零会因 `memory` 容量等偶合造成指纹碰撞。代价见 §6.4。

### 6.3 已知缺陷（未修，需知悉）

| # | 缺陷 | 影响 | 状态 |
|---|---|---|---|
| 1 | **虚拟化环境六维全 `"0"`** ⇒ 所有容器 / VM 算出**同一个 deviceId** | 统计侧把它们去重成 1 台，**安装量严重低估** | ⚠️ 未修 |
| 2 | `system` 维含 `os.release()`（内核版本） | **内核升级即换 deviceId** → 被统计成一台新设备 | ⚠️ 未修 |
| 3 | 非 root 下 `dmidecode` / `/sys/class/dmi/id/board_serial` 多不可读 | `cpu` / `boardSerial` 常为空串（`matchCount` 偏低） | 设计取舍（不引入提权） |

> 缺陷 1、2 的组合后果：**同一台物理机在内核升级后会被算作新安装**，而**容器化部署的多台机器会被算作同一台**。若要修正，方向是「虚拟化环境也采集可用区分度字段（如宿主机名 / machine-id）+ `system` 改用发行版标识而非内核版本」，但会改变现有 `deviceId` 语义，需与统计端一并评估。

## 7. 标识文件（`device.info`）「写一次 + 自愈校验」

### 7.1 内容

```json
{
  "deviceId": "<sha256 硬件指纹>",
  "createdAt": "2026-09-27T07:51:25.446Z",
  "virtualized": false,
  "hardware": { "system": "…", "cpu": "…", "gpu": "…", "memory": "…", "diskUid": "…", "boardSerial": "…" }
}
```

写入模式 **`0600`**。**普通卸载不清除它**（重装仍视为同一设备）。

### 7.2 校验规则（`checkDeviceFile`）

| 判定 | 条件 | 处理 |
|---|---|---|
| `missing` | 文件不存在 | → 重建 |
| `ok` | `btime` 与 `mtime` 差值 ≤ 2 秒 | **不做任何修改**（连回写都没有） |
| `tampered` | `mtime > btime + 2s` | → 重建 |
| `unknown` | `btime` 不可用 / `btime <= 0` / `btime > mtime`（拿到的是 ctime 回退值）/ `statSync` 抛错 | **放过**——内容可解析就沿用原标识 |

两条关键设计：

1. **只比 `mtime`，绝不比 `ctime`**。`chmod` / `chown` 只改 ctime，安装脚本对目录和文件改权限**不应**被误判为「文件被改写」。（写入用 `mode: 0600` 只动 ctime，因此不会打破判据。）
2. **`btime` 不可用时宁可放过**（`unknown` → 沿用），因为部分文件系统不提供 birth time，Node 会静默回退成 ctime——此时「判据本身不可信」，重建会造成 install 风暴。

### 7.3 重建规则与 24 小时限流

```
需要重建（missing / tampered / 内容不可解析）
        │
        ├─ 重新采集指纹 → 写标识文件（createdAt = 当下，deviceId 按当前硬件重算）
        │
        └─ 距上次重建 ≥ 24 小时？
                ├─ 是 → reportInstall = true（观测标记：本次重建未被限流）
                │       并写 state.lastRebuildAt = 新的 createdAt
                └─ 否 → reportInstall = false（照常重建，标记为「被限流」）
                        且**不顺延** lastRebuildAt
```

- **限流不阻止重建本身**——标识文件必须恢复可用，否则后续 deviceId 全失效。
- **限流窗口不因被限流的重建而顺延**：否则文件被持续改写时，永远等不到窗口结束、也就永远报不出下一次安装事件。
- ★ **v1.35.11 起 `reportInstall` 不再参与 `upapi` 取值**：`install` 与否改由 `resolveUpapi` 比对 `device_uuid` 决定。
  - 于是「同机反复改写标识文件」**天然不会刷高安装量**（硬件没变 ⇒ `deviceId` 没变 ⇒ `heartbeat`）—— 这正是旧版 24h 限流想达成的效果，现在由身份判据覆盖。
  - `reportInstall` / `lastRebuildAt` 仅保留为**可观测标记**（仍写盘、仍打 `[telemetry] …不足 24 小时…` 告警日志），供排查时判断「是被限流了还是硬件真变了」。

### 7.4 ⚠️ 必须「写 `.tmp` → `renameSync`」，不能直接覆写

```ts
const tmp = `${DEVICE_FILE}.tmp`;
fs.writeFileSync(tmp, JSON.stringify(info, null, 2), { encoding: "utf-8", mode: 0o600 });
fs.renameSync(tmp, DEVICE_FILE);
```

**覆写已有文件会复用旧 inode，其 `btime` 保持为最初创建时刻**（Linux ext4 / Windows 皆如此）⇒ 刚重建出来的文件立刻又满足 `mtime > btime + 2s` ⇒ 每次调用都重建，陷入死循环。`rename` 会带上临时文件自己的 `btime`，`btime == mtime` 才成立。

### 7.5 运行态文件（`telemetry-state.json`）为何要独立

| 字段 | 说明 |
|---|---|
| `installReported` | 是否曾**成功**上报过一次安装事件。★ v1.35.11 起只作「从未上报过 ⇒ 必发 `install`」的初判输入 |
| `lastDeviceId` | **v1.35.11 起新增**：上次**成功**上报的 `device_uuid`。**这是 `upapi` 的唯一判据** —— 与当前 `deviceId` 相同 ⇒ `heartbeat`，不同 ⇒ `install`；每次成功上报（含开关切换）都会刷新 |
| `lastReportAt` | 最近一次**成功**上报时间（12h 周期判定依据；v1.35.9 起合并掉恒同值的 `lastActiveAt`，读旧文件时自动回退兼容） |
| `lastRebuildAt` | 最近一次标识文件重建时间（重建限流窗口的基准；v1.35.11 起不再影响 `upapi`） |
| `lastError` | 最近一次上报错误信息 |

若把它们塞进 `device.info`，每次上报都会写文件 → `mtime` 立刻变新 → §7.2 判据立刻判「被改写」→ **「写一次」被自己的运行态打破**。因此拆成两个文件。

**老配置迁移**（`migrateLegacyState`）：老版本把 `installReported` / `lastReportAt` 混存在 `device.info` 里。升级后首次读取时，若运行态尚无 `installReported` 而标识文件里是 `true`，则迁移一次**并顺手把标识文件里的 `deviceId` 写成 `lastDeviceId`**，避免存量部署升级后被误判为「首次安装」。

> ⚠️ 两个**一次性的升级副作用**：
> 1. 老版本因旧逻辑每次心跳都回写 `device.info`，导致其 `mtime ≠ btime`。**升级到 v1.29.0+ 后首次启动会被判为 `tampered` → 重建标识文件**（附带新的 `installedAt`）；若重建后 `deviceId` 变了 ⇒ 报一次 `install`，这是**一次性**的。
> 2. **从 ≤ v1.35.10 升到 v1.35.11** 时，运行态没有 `lastDeviceId`（且老 `device.info` 里可能也没有 `installReported`）⇒ 无法证明「ID 未变」⇒ **保守补发一次 `install`**，写入后即回归正常（一次性）。

## 8. 容错与失败处理

### 8.1 设计原则

- **任何失败都不得影响主业务**：无权限、离线、采集失败、写入失败——全部 `try/catch` 吞掉，只 `console.warn` 或写 `lastError`，**从不抛异常给调用方**。
- `reportOnce` / `reportOnToggle` 的调用点（`server/index.ts` 的 `PUT /api/settings` 用 `.catch(() => {})`）也做了兜底。
- 所有采集命令（`dmidecode` / `lscpu` / `lsblk` / `lspci` / `nvidia-smi` / `systemd-detect-virt`）统一走 `tryExec`：**2 秒超时**、失败/超时返回空串。
- 标识文件 / 运行态文件写入失败只 `console.warn`，不阻断。

### 8.2 失败重试

| 失败类型 | `fatal` | 行为 |
|---|---|---|
| 网络异常 / DNS 失败 / 连接超时（10s） | `false` | 写 `lastError` → **10 分钟后重试** |
| HTTP 5xx | `false` | 同上 |
| HTTP 401 / 403 | **`true`** | 写 `lastError` → **退回 12 小时周期**，不密集重试 |
| 其他非 2xx | `false` | 10 分钟后重试 |
| 上传开关关闭 | **`true`**（`error="上传已关闭"`，v1.35.9 起） | 无请求；**退回 12 小时周期，不再 10 分钟空转**（见 §10） |

**成功的定义**：HTTP 2xx。成功后写 `{ installReported: true, lastDeviceId: info.deviceId, lastReportAt, lastError: undefined }`。

## 9. 排查手册

### 9.1 看状态

```bash
# 4) 开关是否被关掉
grep -A2 telemetry /opt/docker-manager-yanzi/config/settings.json

# 5) 手动强制上报一次（后端接口，前端未接线）

```

关键判读字段：`lastDeviceId`（上次成功上报的 `device_uuid`，**与当前 `deviceId` 比一下就知道下次会不会报 `install`**）、`installReported`（是否成功报过安装）、`lastReportAt`（最近成功时间）、`nextReportAt`（下次计划）、`lastError`（最近错误）。

> ★ **v1.35.11 起怎么判断「该报的是哪种」**：比对 `lastDeviceId` 与当前 `deviceId`（`GET /api/telemetry/status` 给的是实时 `deviceId`；值以标识文件里的 `deviceId` 为准）。
> 相同 ⇒ 下次上报是 `heartbeat`；不同或 `lastDeviceId` 缺失 ⇒ 下次是 `install`。
> **「后台日志里每次启动都有一条 `install`」在 v1.35.11 起属异常**（正常应是 `heartbeat`）—— 除非刚装 / 刚重建过标识文件。

### 9.2 常见现象与判据

| 现象 | 判读 |
|---|---|
| `lastError: "fetch failed"` / `ENOTFOUND` | **正常**——端点 `yanzi-api.ziruxue.top` 及旧 `docker-yanzi.ziruxue.top` 当前**均为 NXDOMAIN、接口未开放**。根域 `ziruxue.top` → `60.205.251.18` 可解析，说明出口 DNS 正常，纯粹是端点未就绪 |
| 报 `HTTP 502` 且域名不存在 | ⚠️ **先怀疑本机 HTTP 代理伪造**：`http_proxy` / `https_proxy`（如 `127.0.0.1:57142`）对任何不可达域名都返回同一张 502 兜底页。判「服务挂了」之前必须 `nslookup` + 用一个**确定不存在**的域名做对照 |
| **每次重启都报一次 `install`** | ❌ **v1.35.11 起属异常**（`device_uuid` 未变时应为 `heartbeat`）。判读顺序：① 看 `telemetry-state.json` 有没有 `lastDeviceId` —— **缺失** ⇒ 升级后的**一次性**补发，下一次即正常；② 有 `lastDeviceId` 但与 `device.info` 里的 `deviceId` **不同** ⇒ 标识文件被重建过（硬件 6 维变了？见「`deviceId` 突然变了」行）；③ 两者相同却在报 `install` ⇒ 版本没升上去（老客户端） |
| 1 小时内报了好几次 install | 现在只可能是 **`device_uuid` 真的变了**（否则不会报 install）。检查是否有外部脚本 / 备份工具在改写 `device.info` 且**同时**硬件 6 维发生变化；也留意「打开设置页」会触发一次标识文件校验与**重建**（§2.1 第 8 条），重建后若 `deviceId` 变了就会报 install |
| `deviceId` 突然变了 | ① 内核升级（§6.3 缺陷 2）② 换了硬盘 / 内存 / GPU（6 维变了）③ 标识文件被重建 |
| 卡片里「主板型号 / 产品序列号 / 系统UUID」显示「—」 | 非 root 读不到 DMI ⇒ 需**重跑 `install.sh`** 安装最新 systemd 单元（OTA 不更新单元文件） |
| 关闭开关后仍有请求 | 只应出现在**切换的那一刻**（§3.3）；之后应完全静默。若持续有请求 → 检查 `settings.json` 是否真的写入了 `telemetry.enabled: false` |
| `matchCount` 偏低 | 非 root 下 `dmidecode` 受限，`cpu` / `boardSerial` 常空，属预期 |

| ~~「每次启动都发 `install`」~~ **已根治（v1.35.11）** | 旧模型下端点长期不可达 ⇒ `installReported` 永不置位 ⇒ 所有触发都报 `install`。v1.35.11 起 `upapi` **只由 `device_uuid` 是否变化决定**：**每次重启都是 `heartbeat`**，只有首次安装 / 身份变化才 `install`（§2.1、§2.2） |
| **安装量语义** | `install` 次数 ≈ **去重后的设备数**（每次重启不再重复计数）。服务端仍建议以 `device_uuid` upsert ＋ 比对 `installedAt`（标识文件创建时间）为准，并注意**开关切换仍会发 `install`**（唯一例外，可用载荷 `uploadEnabled` 字段区分） |
| **升级一次性补发** | 从 ≤ v1.35.10 升到 v1.35.11 时运行态无 `lastDeviceId` ⇒ 保守补发一次 `install`（一次性，见 §7.5） |

## 附录 A — 一次典型生命周期（时序）

```
① 安装（install.sh）
   └─ 首次启动 → startTelemetryHeartbeat() → 30s 后 reportOnce("startup")
        ├─ device.info 不存在 → 采集指纹 → 写文件（createdAt = 安装时间）⇒ 新的 deviceId
        ├─ resolveUpapi(state, deviceId)：state.installReported=false ⇒ "install"
        └─ POST … /event  body = { upapi:"install", … }  → 2xx
              └─ state: installReported=true, lastDeviceId=<deviceId>, lastReportAt=now
              └─ 下一次调度：12 小时后

② 12 小时后
   └─ reportOnce("periodic") → dueForPeriodic=true
        └─ lastDeviceId == deviceId ⇒ POST  body = { upapi:"heartbeat", … }

③ NAS 重启（systemd restart）
   └─ 30s 后 reportOnce("startup")
        ├─ device.info 校验 ok（btime==mtime）→ 不重建 ⇒ deviceId 不变
        └─ lastDeviceId == deviceId ⇒ body.upapi="heartbeat"   ← ★ 重启不再报 install（v1.35.11）

④ 用户把上传开关从「开」改成「关」并点 APPLY
   └─ PUT /api/settings → prevEnabled(true) != nextEnabled(false)
        └─ reportOnToggle(false)：强制绕过守卫，**只发 1 条**
             └─ POST  body.upapi="install"  body.uploadEnabled=false   ← 开关切换恒 install（唯一例外）
        └─ 之后：周期性上报全部静默（定时器退回 12 小时周期，不再 10 分钟空转）

⑤ 用户再改成「开」
   └─ PUT /api/settings → reportOnToggle(true)
        └─ POST  body.upapi="install"  body.uploadEnabled=true
        └─ 12 小时周期恢复正常

⑥ 标识文件被删 / 被改写（tampered）后重启
   └─ getDeviceInfo() 重建标识文件 ⇒ createdAt / deviceId 按**当前硬件**重算
        ├─ 重建后 deviceId 与 lastDeviceId **相同** ⇒ body.upapi="heartbeat"
        └─ 重建后 deviceId **不同**    ⇒ body.upapi="install"（＝真·身份变化）
```

> 注意 ⑥ 的细节：`deviceId` 只在**标识文件被重建**时才重算，且重算结果取决于**当时的硬件 6 维**。
> 单纯重写内容（硬件没变）⇒ 重建后 `deviceId` 相同 ⇒ 报 `heartbeat`，安装量不受影响；
> 只有硬件 6 维真的变了（换盘 / 换内存 / 内核升级使 `system` 维度变化等）⇒ `deviceId` 才不同 ⇒ 报 `install`。
