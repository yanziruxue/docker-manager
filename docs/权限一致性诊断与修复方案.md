# 权限一致性诊断与修复方案

> **状态：已实施（v1.18.0）。** 本文保留为设计与决策记录；实际实现见 `server/perms.ts`、`server/perms-cli.ts`、`server/backup.ts`、`server/index.ts`、`src/pages/Settings.tsx`。
>
> 面向 v1.18.0（Minor）。起因：生产「立即备份」跳过 `qinglong/.stack-meta.json（EACCES）`，提示信息不足以定位，且缺乏修复手段。

## 一、问题与根因

### 现象
备份成功，但 `skipped` 里有 `qinglong/.stack-meta.json（EACCES）`——只有错误码，看不出是权限位问题还是属主问题，也没有修复路径。

### 根因
备份链路 `stageConfig() → copyTree() → fs.copyFileSync()` 中，**只有读取源文件这一步需要源文件的读权限**；目标端（`/tmp` 暂存）由本进程新建，写与清理都有 `chmodTree()` / `rmrf()` 兜底。所以 EACCES 必然来自**源文件对运行用户不可读**：

| 成因 | 特征 | 应用能否自修 |
|---|---|---|
| 属主与运行用户不一致（如 root 属主 0600） | `st.uid !== process.getuid()` | ❌ 需 root |
| 属主正确但权限位无 `r`（如 0000） | `st.uid === getuid()` 且 `!mode & 0o400` | ✅ `chmod u+r` |
| 父目录无 `x` 权限 | 连 `lstat` 都失败 | ❌ 需 root |

### 部署事实（决定修复目标）
- 服务以专用系统用户运行：`User=docker-manager-yanzi`（`useradd -r -s /sbin/nologin`）
- `INSTALL_DIR=/opt/docker-manager-yanzi`，`DATA_DIR=<install>/data`，`COMPOSE_DIR=<data>/dockercompose`
- 安装时 `install.sh` 对 `INSTALL_DIR` 做过一次 `chown -R`

> 关键：**`fix-perms` 以 sudo 运行时 `process.getuid()` 是 0**，目标属主必须取
> `INSTALL_DIR` 的属主（`fs.statSync(INSTALL_DIR).uid`），不能取当前进程 uid。

## 二、设计目标

1. 失败信息**自解释**：一眼看出「谁的权限不对、差在哪一位」
2. 能自动修的**自动修**（属主正确、仅缺读位）
3. 不能自动修的，给出**可直接复制粘贴**的修复命令
4. 提供 `sudo` 一键修复入口，处理属主漂移
5. 全程不扩大文件暴露面（**绝不**把 0600 的敏感文件改成 0644）

## 三、方案总览（四层）

| 层 | 触发时机 | 动作 | 权限要求 | 默认 |
|---|---|---|---|---|
| **L1 自愈** | 备份复制遇 EACCES | 属主是当前用户且缺读位 → `chmod u+r` 后重试一次 | 属主 | 开（可关） |
| **L2 诊断+命令** | L1 失败或前提不符 | 结构化 `skippedDetails` + 生成修复命令 | — | 开 |
| **L3 一键修复** | 用户手动 `sudo … fix-perms` | 递归 chown 到服务用户 | root | 手动 |
| **L4 启动体检** | 服务启动 + 新端点 | 扫描属主异常条目，日志 WARN + 界面提示条 | 只读 | 开 |

## 四、详细设计

### 4.1 新增 `server/perms.ts`

```ts
export interface PermIssue {
  relPath: string;      // qinglong/.stack-meta.json
  absPath: string;      // /opt/docker-manager-yanzi/data/dockercompose/qinglong/.stack-meta.json
  code: string;         // EACCES
  mode: string;         // "600"
  uid: number;          // 0
  gid: number;          // 0
  owner: string;        // "root"
  procUid: number;      // 998
  procUser: string;     // "docker-manager-yanzi"
  reason: string;       // 人类可读的判定
  advice: string;       // 可直接复制的修复命令
  autoFixed: boolean;   // L1 是否已修好
}
```

核心函数：

- `currentUser()` — `process.getuid()` + `os.userInfo()`，nologin 环境下也能拿到名字
- `userNameOf(uid)` — 解析 `/etc/passwd`（0644 可读，不依赖 `getent`）
- `diagnosePerm(path, rel, code, autoFixed)` — 用 **`lstatSync`**（只需父目录 `x`，不需要文件读权限）判定 `byOwner` / `noRead`，产出 `reason` + `advice`

**文案模板**（skipped 字符串，保持 `string[]` 兼容）：

```
qinglong/.stack-meta.json — 拒绝访问（EACCES）：权限 600，属主 root(uid 0)，当前进程 uid 998(docker-manager-yanzi)
```

**`advice` 生成规则**：

| 情况 | 命令 |
|---|---|
| 属主不一致 | `sudo chown 998:998 '<abs>'` |
| 属主一致缺读位 | `sudo chmod u+r '<abs>'` |
| 父目录缺 `x` | `sudo chmod u+x '<父目录>'` |

### 4.2 L1 自愈（`server/backup.ts` 的 `copyTree` 文件分支）

```ts
} else if (entry.isFile()) {
  try {
    fs.copyFileSync(s, d);
  } catch (e: any) {
    if (isPermError(e) && tryGrantOwnerRead(s)) {
      fs.copyFileSync(s, d);          // 修好后重试一次
      autoFixed = true;
    } else throw e;
  }
}
```

```ts
function tryGrantOwnerRead(p: string): boolean {
  const st = fs.statSync(p);
  const uid = process.getuid?.();
  if (uid === undefined || st.uid !== uid) return false;  // 属主不是我们 → chmod 无意义
  if (st.mode & 0o400) return false;                      // 本来就有读权限 → 不是这个问题
  fs.chmodSync(p, (st.mode & 0o777) | 0o400);             // 只补属主读位
  log.warn(`已为备份自动补上属主读权限：${p}`);
  return true;
}
```

**安全边界**（必须遵守）：
- 只 `| 0o400`，**只加属主读位**；group/other 位不动，uid/gid 不动
- 原 `0000` → `0400`，仍是「仅属主可读」，暴露面不变
- 属主不是运行用户时**直接放弃**，不做任何 chmod
- 设置项 `backup.autoFixReadPerm`（默认 `true`）可关


### 4.4 L3 一键修复子命令（`index.ts` 顶部 CLI 分支）

```bash
sudo /opt/docker-manager-yanzi/docker-manager-yanzi fix-perms [选项]
  --dry-run          只列出将修改的项，不落盘（默认先打印再执行）
  --path <dir>       指定目录（默认 DATA_DIR / LOG_DIR / CONFIG_DIR）
  --uid <n>          目标属主（默认取 INSTALL_DIR 的属主）
  --normalize-mode   额外把目录归一化为 0755、文件 0644（默认只 chown）
```

行为：
1. `--dry-run` 或首次运行时列出清单：`将修正 <path>：uid 0 → 998`
2. 递归遍历：属主 != 目标 uid → `chownSync`；**默认不动权限位**
3. 若 chown 后仍不可读（属主已对但缺位）→ 补 `u+rw`（`--normalize-mode` 时才全量归一化）
4. 输出统计：`检查 128 项；属主修正 3；权限修正 1；跳过 0；失败 0`
5. 退出码：有失败 → 1，便于脚本判断

> 默认**不**归一化权限位，就是为了避免把 0600 的密钥文件改成 0644。

### 4.5 L4 启动体检 + 端点

- 启动时 `scanPermIssues(COMPOSE_DIR)`（只扫一层 + 堆栈内非目录文件），有异常打 WARN，无异常静默
- 新增 `GET /api/system/permission-check` → `{ ok, checked, issues: PermIssue[] }`（结果缓存 60s）
- 前端在备份卡片顶部显示黄色提示条：`检测到 N 个文件权限异常（备份时可能被跳过）` + 「复制修复命令」「重新检测」

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| chmod 扩大敏感文件暴露面 | 只补 `u+r`，绝不碰 group/other；归一化需显式 `--normalize-mode` |
| 自动修改用户文件权限引起意外 | 默认开启但可关；每次修改都写 WARN 日志；仅属主是自身时才动 |
| `fix-perms` 在 sudo 下把属主设成 root | 目标 uid 取 `INSTALL_DIR` 属主，不取 `process.getuid()`；`--dry-run` 先行确认 |
| SEA 下 `process.argv` 索引差异 | CLI 判定用 `process.argv.slice(1)`，不用固定下标；打包后用 `--version` 冒烟验证 |
| 老设置文件无新字段 | `settings.ts` 走 `{ ...DEFAULTS.backup, ...parsed.backup }` 归并，天然兼容 |
