# 用户登录与密码找回方案

> 适用版本：v1.13.0（登录鉴权）+ v1.14.0（密码找回码）+ v1.30.3（找回码 18 → 24 位，重置入口兼容旧 18 位）+ **v1.31.0（找回码收敛为 18~24 位并区分大小写；升级后强制重走账号初始化）**
> 涉及模块：`server/{users,auth,index}.ts`、`src/App.tsx`、`src/api.ts`、`src/components/auth/{SetupWizard,LoginPage}.tsx`、`src/lib/recovery-code.ts`、`src/pages/Settings.tsx`
> 本文档合并原《密码找回码实现方案.md》，登录与找回两套凭证体系统一在此说明。

---

## 0. 总览

docker-manager 是**自托管 NAS 场景**的单管理员工具：一台机器、一个管理员账号、没有邮件服务、可能常年只在内网访问。因此登录体系按「够用且不过度设计」取舍：

| 维度 | 选择 | 理由 |
|---|---|---|
| 用户规模 | **单管理员**（`role: "admin"` 固定） | 个人/家庭自托管；不做多用户与角色 |
| 凭证 | 用户名 + 密码（主） + **18~24 位找回码**（备） | 密码忘了还有离线自救通道 |
| 密码存储 | `scrypt` + 独立 16B salt，**仅存哈希** | 落盘文件泄露也不泄露明文 |
| 会话 | **服务端内存 Map** + `httpOnly` Cookie | 零外部依赖；重启即失效（可接受） |
| 会话时长 | `settings.user.sessionTimeout`（默认 30 分钟） | 用户可调，下次登录生效 |
| 找回方式 | 离线找回码（**18~24 位、区分大小写**），**不用邮箱/短信** | NAS 通常没有邮件服务 |
| 凭据版本 | `credentialVersion`（本版要求 **2**） | 老库升级后**强制重走一次账号初始化**（见第三部分） |

两套凭证的关系：

```
密码      —— 主钥匙：日常登录、改密、设置找回码都要它
找回码    —— 备用钥匙：仅用于「忘记密码 → 重置密码」，不能用来登录
```

## 1. 设计定位与约束

| 约束 | 影响 |
|---|---|
| 单进程、单管理员 | 会话放内存即可，无需 Redis/数据库；不做多用户/角色/权限组 |
| 无外部服务依赖 | 找回不靠邮件验证码，改用离线找回码 |
| 部署形态为**同源单端口**（二进制内嵌前端） | CORS 用默认 `cors()` 亦可；若改为前后端分离跨域部署，需显式配置 `origin`（见 §13 限制） |
| 可能暴露到公网 | 需要防用户名枚举、防时序攻击、找回码限流 |

## 2. 用户与凭证数据模型

账户独立于 `settings.json`，存于 `<data>/users.json`（与设置分离，避免备份/迁移设置时把账户一起带上）：

- 路径：`dataPath("users.json")`，即 Linux 部署下 `<data>/users.json`
- 落盘权限：`0o600`（`saveUsers` 内 `chmodSync`，失败不影响功能）
- 首次启动 `ensureUsersDir()` 保证文件存在但内容为空数组 → 前端进入初始化向导

```ts
// server/users.ts
export interface UserRecord {
  id: string;
  username: string;
  role: "admin";              // 固定单管理员
  passwordHash: string;       // scrypt 哈希，hex（64B）
  salt: string;               // 随机 16B，hex
  createdAt: string;

  // ↓ v1.14.0 新增，未设置时全部为 undefined
  recoveryHash?: string;        // 找回码 scrypt 哈希（hex，64B）
  recoverySalt?: string;        // 找回码 salt（hex，16B）
  recoverySetAt?: string;       // 最近一次设置时间
  recoveryLastUsedAt?: string;  // 最近一次用于重置的时间（限流用）
}
```

落盘示例（**无任何明文字段**）：

```json
{
  "id": "e56b9f46-57a4-40a3-9408-3ef52a45a2d9",
  "username": "admin",
  "role": "admin",
  "passwordHash": "9f2a…",
  "salt": "c71d…",
  "createdAt": "2026-09-07T14:20:11.203Z",
  "recoveryHash": "b83e…",
  "recoverySalt": "4a10…",
  "recoverySetAt": "2026-09-07T14:27:07.589Z",
  "recoveryLastUsedAt": "2026-09-07T14:31:42.117Z"
}
```

> **历史兼容**：旧版本 `settings.json` 里的 `user.username` 已降级为历史字段，不再展示/编辑；账户一律以 `users.json` 为准。

## 3. 密码存储与校验

```ts
// server/users.ts
export function hashPassword(password: string): { hash: string; salt: string } {
  const salt = crypto.randomBytes(16);
  const hash = crypto.scryptSync(password, salt, 64);   // Node 默认 N=16384, r=8, p=1
  return { hash: hash.toString("hex"), salt: salt.toString("hex") };
}

export function verifyPassword(password: string, record: UserRecord): boolean {
  try {
    const salt = Buffer.from(record.salt, "hex");
    const expected = Buffer.from(record.passwordHash, "hex");
    const actual = crypto.scryptSync(password, salt, 64);
    return expected.length === actual.length && crypto.timingSafeEqual(expected, actual);
  } catch { return false; }
}
```

要点：

- **每账号独立随机 salt**，杜绝彩虹表；改密码时会重新生成 salt。
- **`timingSafeEqual` 常量时间比较**，避免按字节逐位提前返回造成的时序侧信道。
- 密码规则：**≥ 6 位**（初始化、改密、找回重置三处一致校验），无复杂度强制要求。
- 用户名查找 **忽略大小写**（`getUserByUsername` 内 `trim().toLowerCase()` 比对），但保留注册时原样。

## 4. 会话机制（`server/auth.ts`）

```
登录成功 → crypto.randomBytes(32).toString("hex") 作 token
         → sessions.set(token, { userId, expiresAt: now + TTL })
         → Set-Cookie: docker-manager-yanzi_session=<token>; HttpOnly; SameSite=Lax; Path=/; Max-Age=TTL
```

| 项 | 取值 / 行为 |
|---|---|
| Cookie 名 | `docker-manager-yanzi_session` |
| token | 32 字节随机 hex |
| 存储 | 进程内 `Map<token, {userId, expiresAt}>` |
| TTL | `settings.user.sessionTimeout` 分钟，默认 **30**（`Math.max(1, n)` 兜底） |
| 属性 | `httpOnly`（JS 读不到，抗 XSS 窃取）、`sameSite=lax`（抗 CSRF）、`path=/` |
| 过期处理 | 惰性清理：`getSessionUser` 发现过期即 `sessions.delete` |
| 用户被删 | 会话对应的 `findUserById` 为空时一并删除会话 |
| 服务重启 | **会话全部丢失，需重新登录**（内存存储的代价，单管理员场景可接受） |
| TTL 变更时机 | 改动在**下次登录**生效，不影响当前会话 |

> `getSessionUser` 的参数类型放宽为 `{ headers: IncomingHttpHeaders }`，以便 WebSocket 握手请求（`IncomingMessage`）与 Express `Request` 共用同一个会话解析函数。

## 5. 鉴权边界

服务端有**两层**中间件，注册顺序即生效顺序：

```
cors() → express.json()
   ↓
【第 1 层】「账号待重新初始化」拦截（v1.31.0）  —— 仅放行白名单，其余 403 REINIT_REQUIRED
   ↓
【第 2 层】全局守卫 —— /api/auth/* 放行，其余要求登录
   ↓
业务路由（auth 路由 → 引擎/容器/堆栈/镜像/… 路由）
```

### 5.1 「账号待重新初始化」拦截（v1.31.0）

```ts
// server/index.ts —— 必须紧跟 cors()/express.json()，且必须在所有 /api/auth/* 路由注册之前
const REINIT_ALLOWED_AUTH = new Set([
  "/auth/init-status", "/auth/login", "/auth/logout",
  "/auth/me", "/auth/reinit", "/auth/reset-by-recovery",
]);

app.use("/api", (req, res, next) => {
  if (!requiresAccountReinit()) return next();                 // 无待重设账号 → 完全跳过
  const p = req.path.replace(/\/+$/, "") || "/";               // 容忍尾斜杠，避免 `…/me/` 绕过
  if (REINIT_ALLOWED_AUTH.has(p)) return next();               // 白名单
  res.status(403).json({
    success: false,
    code: "REINIT_REQUIRED",
    error: "请先完成账号重新设置（用户名 / 密码 / 找回码）",
  });
});
```

> ⚠️ **顺序是硬要求，不是风格问题**：Express 按注册顺序依次执行中间件。首次实现时把这段加在了「原全局守卫」的位置（即 `/api/auth/*` 路由**之后**），结果 `POST /api/auth/recovery` 命中了自身路由、直接返回 `400 格式错误` 而非 `403 REINIT_REQUIRED` —— 拦截形同不存在。**新增任何 `/api/...` 路由前，都要确认自己没有插到这一层之前。**

拦截范围 = **除白名单外的所有 `/api` 路径**，包括：

| 类别 | 例子 | 未重设时的响应 |
|---|---|---|
| 业务接口 | `/api/engines`、`/api/containers`、`/api/stacks`、`/api/settings`、`/api/telemetry/*` | `403 REINIT_REQUIRED` |
| 未进白名单的 auth 接口 | `POST /api/auth/password`、`GET/POST/DELETE /api/auth/recovery` | `403 REINIT_REQUIRED` |

白名单里**必须**有 `reset-by-recovery`：否则密码已忘、账号又待重设的用户会**同时被两把锁关在门外**（进不去系统，也没法用找回码重置）。它本身是公开路由、靠找回码哈希比对与 10 分钟限流自保，放行不降低安全性。

### 5.2 全局守卫 + `/api/auth` 豁免

```ts
// server/index.ts
app.use("/api", (req, res, next) => {
  if (req.path.startsWith("/auth")) return next();   // 放行，由路由自行判断
  return requireAuth(req, res, next);
});
```

> ⚠️ **实现要点**：`/api/auth/*` 整体豁免于全局守卫，因此**需要登录的 auth 路由必须自己挂 `requireAuth`**（`POST /api/auth/password`、`GET/POST/DELETE /api/auth/recovery` 均已显式挂载）。新增 auth 路由时若漏挂，等于开了个未鉴权后门。

### 5.3 WebSocket 终端

`/ws/terminal` 不走 Express 中间件链，握手时**单独校验会话**：

```ts
wss.on("connection", async (ws, req) => {
  if (!getSessionUser(req)) { ws.close(1008, "Unauthorized"); return; }
  …
});
```

未登录时以 1008（policy violation）关闭，不给终端数据流。

### 5.4 前端联动

- `src/api.ts` 的 `request()` 统一带 `credentials: "include"`，保证 Cookie 随请求发送。
- 非鉴权接口返回 **401** 时（排除 `/auth/` 前缀，避免登录接口自身 401 触发跳转循环），派发 `auth:unauthorized` 事件；`App.tsx` 监听后清空用户并回到登录页。
- 任何接口返回 **403 且 `code === "REINIT_REQUIRED"`** 时，派发 **`auth:reinit-required`** 事件；`App.tsx` 监听后切到 `reinit` 状态（覆盖「已登录状态下被 OTA 升级」的场景，见第三部分）。
- 主数据加载 effect **依赖 `authState`**，仅在 `authed` 后才拉取引擎/设置等数据 —— 否则未登录时预先拉取必然 401 且登录后不会重试（v1.13.0 踩过的坑）。

## 6. 前端门卫 AuthGate（`src/App.tsx`）

启动并发请求两个接口，**四态分流 + 一个阻塞态**：

```ts
const [init, meRes] = await Promise.all([
  getAuthInitStatus().catch(() => ({ initialized: false, needsReinit: false })),
  getMe().catch(() => null),
]);

if (init.needsReinit) {              // ① 老凭据版本 → 强制重走账号初始化
  if (meRes) setMe(meRes);
  setAuthState(meRes ? "reinit" : "login");   // 已登录直接进重设表单；未登录先去登录
  return;
}
if (meRes)                  → authed   // 有会话，直接进入主应用
else if (!init.initialized) → setup    // 无账号 → 初始化向导
else                        → login    // 有账号无会话 → 登录页
```

> `needsReinit` 判定**先于** `meRes`：否则升级后带着旧会话的用户会直接进入主应用，然后被第一个业务接口的 `403 REINIT_REQUIRED` 顶回来（体验上是"卡住"而不是"引导重设"）。

| 状态 | 渲染 |
|---|---|
| `loading` | 加载占位（避免闪烁到登录页） |
| `setup` | `<SetupWizard onDone={handleAuthDone} />` |
| `login` | `<LoginPage onDone={handleAuthDone} notice={loginNotice} />` |
| `reinit` | `<SetupWizard mode="reinit" initialUsername={me?.username} onDone={handleReinitDone} />` |
| `authed` | 主应用 |

**状态迁移**

- 初始化/登录成功后 `handleAuthDone(user)`：`user.needsReinit` 为真 → `reinit`，否则 → `authed`（服务端已下发会话 Cookie，无需再跳转）。
- reinit 提交成功 → `handleReinitDone()`：清 `me` → 设 `loginNotice`「账号已重新设置，请使用新的用户名和密码登录」→ `login`（**不能直接进主应用**：服务端已把该用户全部会话作废，此时没有任何有效会话）。
- 运行中会话失效 → `auth:unauthorized` → `login`。
- 运行中撞到 `403 REINIT_REQUIRED` → `auth:reinit-required` → 仅当当前是 `authed` 时切 `reinit`（见 §5.4）。
- 登出：`POST /api/auth/logout`（失败也忽略）→ 清空 `me` + 清 `loginNotice` → `login`。
- 顶栏显示当前用户名 + 登出按钮。

## 7. 接口清单

全部挂在 `/api/auth` 下。**公开** = 无需登录；**需登录** = 路由内自行挂 `requireAuth`。

| 方法 | 路径 | 鉴权 | 用途 |
|---|---|---|---|
| `GET` | `/api/auth/init-status` | 公开 | 是否已初始化 + 是否有账号待重设（`{ initialized, needsReinit }`） |
| `POST` | `/api/auth/init` | 公开（仅未初始化时可用） | 创建管理员账号，成功后直接下发会话 |
| `POST` | `/api/auth/login` | 公开 | 用户名 + 密码登录（响应含 `needsReinit`） |
| `POST` | `/api/auth/logout` | 公开 | 销毁会话 + 清 Cookie |
| `GET` | `/api/auth/me` | 公开（无会话返 401） | 当前登录用户 |
| `POST` | `/api/auth/reinit` | **需登录** | **重新初始化账号：覆盖用户名 / 密码 / 找回码，并作废该用户全部会话**（见 §7.4） |
| `POST` | `/api/auth/password` | 需登录 | 修改密码（校验原密码） |
| `GET` | `/api/auth/recovery` | 需登录 | 找回码状态 |
| `POST` | `/api/auth/recovery` | 需登录 | 设置/重设找回码（需当前密码） |
| `DELETE` | `/api/auth/recovery` | 需登录 | 清除找回码 |
| `POST` | `/api/auth/reset-by-recovery` | **公开** | 用找回码重置密码 |

> 上表中「需登录」的 auth 路由同时受 **§5.1 的 `REINIT_REQUIRED` 拦截**约束：账号待重设时，只有 §5.1 白名单里的 6 个路径可用。

### 7.1 POST `/api/auth/init` — 初始化

请求：`{ username, password, recoveryCode? }`

```
1. countUsers() > 0              → 409「系统已初始化」
2. 缺用户名/密码                  → 400「缺少用户名或密码」
3. password.length < 6           → 400「密码至少 6 位」
4. recoveryCode 非空 → 格式校验   → 400（格式错误详情）
5. createUser(...) → createSession(res, user.id) → 200 { id, username, role }
```

`recoveryCode` **可选**：留空可稍后在「系统设置 → 用户 → 密码找回码」补设。

### 7.2 POST `/api/auth/login` — 登录

请求：`{ username, password }`

```
用户不存在 或 verifyPassword 失败 → 401「用户名或密码错误」（统一文案，防用户名枚举）
成功 → createSession + 200 { id, username, role }
```

### 7.3 POST `/api/auth/password` — 修改密码（需登录）

```
1. newPassword 缺失或 < 6 位       → 400「新密码至少 6 位」
2. 用户不存在                      → 404「用户不存在」
3. verifyPassword(oldPassword) 失败 → 400「原密码错误」
4. updateUserPassword（重新生成 salt + 哈希）→ 200
```

### 7.4 POST `/api/auth/reinit` — 重新初始化账号（需登录，v1.31.0）

请求：`{ username, password, recoveryCode }`（三者**均必填**）

```
1. requireAuth                       → 401（无会话）
2. !needsReinit(record)              → 409「账号已完成重新设置」
3. 用户名 / 密码 / 找回码 逐项校验    → 400（与初始化同一套文案）
4. reinitUser(id, input)
     · 覆盖 username / passwordHash+salt / recoveryHash+salt
     · 保留 id 与 createdAt；写 credentialVersion = 2
     · 清 recoveryLastUsedAt（重设即解除找回限流）
5. destroySessionsForUser(userId)    → 作废该用户【全部】会话（含其他设备）
6. destroySession(req, res)          → 连当前会话一并作废 + 清 Cookie
7. → 200 { success: true }
```

**为什么必须「先登录旧账号」而不是做成公开接口**：实例通常暴露在内网甚至公网。若 `reinit` 无需鉴权，任何能打开页面的人都能把管理员账号改成自己的 —— 等于一条无凭证的接管通道。以 `requireAuth` 为门槛后，攻击者需**先知道旧密码或旧找回码**，而这恰好就是「合法持有者」的定义。

**为什么要把全部会话作废**：用户名和密码都变了，旧会话继续有效会让「改密」失去意义（比如密码疑似泄露时，用户重设后攻击者手上的会话仍能继续操作）。

### 7.5 GET `/api/auth/me` / POST `/api/auth/logout`

- `me`：无有效会话 → 401「未登录」；有效 → `{ id, username, role }`
- `logout`：删除会话 + `clearCookie`，恒返回 200

## 8. 账号设置向导（`SetupWizard.tsx`）

同一个组件承担两种场景，由 `mode` 区分；字段构成一致（用户名 / 密码 / 确认密码 / 找回码），差异在提示、必填性与提交目标：

| | `mode="create"`（默认） | `mode="reinit"`（v1.31.0） |
|---|---|---|
| 触发 | 首次部署、无任何账号 | 老凭据版本账号登录后强制进入（§6） |
| 标题 | 初始化向导 | **账号重新设置** |
| 提示条 | 无 | 琥珀色：说明本次升级要求重设用户名 / 密码 / 找回码 |
| 用户名 | 必填（空值） | 必填，**预填当前用户名**（`initialUsername`） |
| 密码 | ≥ 6 位，两次一致 | 同左 |
| 找回码 | **可选**（留空可稍后补设） | **必填** |
| 提交接口 | `POST /api/auth/init` | `POST /api/auth/reinit` |
| 成功后 | 直接进主应用（已有会话） | 回登录页（**全部会话已作废**） |

- 三个字段的校验规则与后端共用同一套文案（找回码走 `src/lib/recovery-code.ts`）。
- 找回码输入带 `n/24` 实时计数；规则见第二部分（18~24 位、区分大小写）。

> 首次部署时**建议就设好找回码** —— 这是唯一一次「不需要当前密码就能设码」的机会，之后在设置页重设都要求当前密码。

## 9. 登录 / 使用 / 失效时序

```
【首次部署】无账号 → SetupWizard → 填用户名/密码/(找回码)
        → POST /api/auth/init → 建号 + 下发会话 → 主应用

【日常登录】有会话 → GET /auth/me 成功 → 主应用（无感）
           无会话 → LoginPage → POST /api/auth/login → Set-Cookie → 主应用

【使用期间】任意 /api 请求带 Cookie → requireAuth 校验内存会话 → 200 / 401
          终端 ws://…/ws/terminal 握手 → getSessionUser 校验 → 放行 / close(1008)

【会话失效】超时 / 服务重启 → 任意接口 401 → 前端派发 auth:unauthorized → 回登录页

【主动登出】顶栏「登出」→ POST /api/auth/logout → 清 Cookie → 回登录页
```

# 第二部分：密码找回码

> 原《密码找回码实现方案.md》内容，自 v1.14.0 起生效。

---

## 10. 背景与目标

登录鉴权上线后，密码一旦遗忘将无法进入系统。由于是**自托管 NAS 场景**，通常没有邮件服务，无法通过「邮箱验证码」找回。

本方案提供一条**离线、自持、无需外部依赖**的密码找回通道：用户在初始化或设置页设置一个 **18~24 位找回码**（Recovery Code，区分大小写），忘记密码时可凭它重置登录密码。

**设计目标**

| 目标 | 做法 |
|---|---|
| 可离线使用 | 不依赖邮件/SMS/第三方服务 |
| 与密码同级保护 | scrypt 哈希存储，明文不落盘 |
| 不泄露用户名 | 错误文案统一，防用户名枚举 |
| 防爆破/滥用 | 10 分钟使用间隔限流 |
| 用户可控 | 可随时重设、清除；重设即解除冷却 |
| **规则不散落** | 四个入口共用 `validateRecoveryCode`，前端同构实现（v1.31.0） |

---

## 11. 找回码规则

| 项 | 规则 |
|---|---|
| 长度 | **18 ~ 24 位**（`RECOVERY_MIN_CODE_LENGTH = 18` / `RECOVERY_MAX_CODE_LENGTH = 24`）；输入期即按 24 截断 |
| 字符集 | **仅字母和数字**（`[A-Za-z0-9]`） |
| 大小写 | **区分大小写**（`AbC…` 与 `aBc…` **不等价**）—— v1.31.0 起 |
| 入口一致性 | **四个入口同一套判定**（首次初始化 / 账号重设 / 设置重设 / 用码重置密码），无「严格 / 放宽」之分 |
| 旧记录兼容 | 历史记录是按**大写**形式哈希的；输入**全小写**时额外回退试一次大写变体（见 §11.1） |
| 存储 | scrypt 哈希 + 随机 16B salt，**明文不落盘、也不可回显** |
| 使用 | 可重复使用，两次使用间隔 **10 分钟** |

> **为什么从「必须满 24 位」退回「18~24 位」**：v1.30.3 把长度钉死在 24 位，并为此引入了「重置入口额外放行 18 位」的 `allowLegacy` 分支 —— 一个入口两套规则。v1.31.0 改为**区间**后，18 位本身就在合法范围内，`allowLegacy` 与 `RECOVERY_LEGACY_CODE_LENGTH` 常量一并删除，规则重新收敛为单条。

### 11.1 大小写语义与历史记录回退（重要）

> **v1.31.0 起：区分大小写 = 比对时逐字节敏感，不做任何大小写归一化。**

这是本模块**第二次**调整语义，两次的区别必须分清：

| 版本 | `normalizeRecoveryCode` | 效果 |
|---|---|---|
| v1.14.0 → v1.30.3 | `trim().toUpperCase()` | 忽略大小写：`abc…` 与 `ABC…` 等价（**存储与比对都按大写**） |
| **v1.31.0 起** | **`trim()`** | **区分大小写**：输入什么就按什么哈希、按什么比对 |

- **前端**：`sanitizeRecoveryInput()` 只做两件事 —— 剔除非字母数字字符、截断到 24 位。**保留用户输入的原始大小写**，界面上也如实回显。
- **服务端**：`normalizeRecoveryCode()` 仅 `trim()`，不做大小写变换。
- **文案**：登录页与设置页均明示「**区分大小写，请按设置时的原始大小写输入**」。

**历史记录的兼容回退**（`legacyUpperVariants()`）

库里现存的老记录是按「转大写后哈希」写入的。若直接改成大小写敏感，这批用户的找回码会**立刻全部失效** —— 而找回码恰恰是「忘密码」时的最后一条通道，等于把他们永久锁死。因此 `verifyRecoveryCode()` 改为**多候选比对**：

```ts
// server/users.ts
function legacyUpperVariants(code: string): string[] {
  const c = normalizeRecoveryCode(code);     // trim()
  const up = c.toUpperCase();
  return up === c ? [] : [up];               // 自身已全大写 → 不给变体（避免无意义多算一次）
}

export function verifyRecoveryCode(code: string, record: UserRecord): boolean {
  if (!record.recoveryHash || !record.recoverySalt) return false;
  const candidates = [normalizeRecoveryCode(code), ...legacyUpperVariants(code)];
  const salt = Buffer.from(record.recoverySalt, "hex");
  const expected = Buffer.from(record.recoveryHash, "hex");
  return candidates.some((c) => {
    const actual = crypto.scryptSync(c, salt, 64);
    return expected.length === actual.length && crypto.timingSafeEqual(expected, actual);
  });
}
```

| 记录类型 | 输入 | 结果 | 说明 |
|---|---|---|---|
| **老记录**（按大写哈希） | 全小写 | ✅ 200 | 回退变体命中 |
| **老记录** | 混合大小写 | ❌ 401 | 老逻辑只存了大写形式，**原始大小写无从还原**（已知限制） |
| **新记录**（按原样哈希） | 错大小写 | ✅ 401 | 大写变体 ≠ 原码 ⇒ **敏感度未被削弱** |
| **新记录** | 原样 | ✅ 200 | 正常命中 |

> 回退**只加候选、不改规则**：新记录永远是「原样」优先命中，多出来的变体只可能在老记录上生效。用全大写的码做基准时，其小写输入的「大写变体」恰好等于原码 —— **写测试用例时必须用混合大小写的码**，否则会误判成「大小写不敏感」。

### 11.2 校验顺序

判定必须**先非法字符、再长度**，否则「24 位里含符号」会被误报成「未满 18 位」，提示与实际问题不符。

```ts
// server/users.ts（v1.31.0）
export const RECOVERY_MIN_CODE_LENGTH = 18;
export const RECOVERY_MAX_CODE_LENGTH = 24;

export function validateRecoveryCode(code: string): string | null {
  const raw = (code || "").trim();
  if (!raw) return "请输入找回码";
  if (!ALNUM_RE.test(raw)) return "找回码仅支持字母和数字";                        // ① 先判字符
  if (raw.length < RECOVERY_MIN_CODE_LENGTH || raw.length > RECOVERY_MAX_CODE_LENGTH) {
    return `找回码需 ${RECOVERY_MIN_CODE_LENGTH}~${RECOVERY_MAX_CODE_LENGTH} 位`; // ② 再判区间
  }
  return null;
}
```

前端 `src/lib/recovery-code.ts` 是同构的等价实现（同样的判定顺序与文案）。

### 11.3 规则演进史（v1.14.0 → v1.31.0）

| 版本 | 长度 | 大小写 | 入口差异 |
|---|---|---|---|
| v1.14.0 | **必须满 18 位** | 忽略（服务端归一化为大写） | 无 |
| v1.30.3 | **必须满 24 位** | 忽略 | 有 —— 重置入口额外接受 18 位（`allowLegacy`） |
| **v1.31.0** | **18 ~ 24 位** | **区分** | **无**（四个入口同一套判定；老记录靠 `legacyUpperVariants` 回退） |

**旧码不会自动迁移**（库里只有 scrypt 哈希，物理上无法知道原码）。用户在「系统设置 → 用户 → 密码找回码」重设一次，即落为「新记录」并享受严格的大小写敏感。

## 12. 找回码哈希实现

与密码**完全同级**：`scrypt` + `crypto.randomBytes(16)` salt + `timingSafeEqual` 防时序攻击。

```ts
function hashRecoveryCode(code: string): { hash: string; salt: string } {
  const salt = crypto.randomBytes(16);
  const hash = crypto.scryptSync(normalizeRecoveryCode(code), salt, 64);
  return { hash: hash.toString("hex"), salt: salt.toString("hex") };
}
```

`normalizeRecoveryCode()` 在 v1.31.0 起**只有 `trim()`**（区分大小写，见 §11.1）；相应地 `verifyRecoveryCode()` 由「单次比对」改为「原样 + 大写变体」的**多候选比对**，完整实现见 §11.1 代码块。

`setRecoveryCode()` 写入新哈希时**同时清空 `recoveryLastUsedAt`**（重设即解除限流）。

## 13. 找回码后端接口

| 方法 | 路径 | 鉴权 | 用途 |
|---|---|---|---|
| `GET` | `/api/auth/recovery` | 需登录 | 查询状态（是否已设置、设置/使用时间、剩余冷却） |
| `POST` | `/api/auth/recovery` | 需登录 | 设置/重设找回码（需校验当前密码） |
| `DELETE` | `/api/auth/recovery` | 需登录 | 清除找回码 |
| `POST` | `/api/auth/reset-by-recovery` | **公开** | 用找回码重置密码 |

> `/api/auth/*` 全部豁免于全局守卫（见 §5.2），因此**必须在这些路由内部自行判断是否需要登录**，不能依赖全局守卫。
> 另注意：账号待重设时（§5.1），除白名单外这些路由会**先**被 `403 REINIT_REQUIRED` 拦下 —— 白名单里与找回码相关的只有 `POST /api/auth/reset-by-recovery`。

### 13.1 GET `/api/auth/recovery` — 查询状态

```jsonc
// 200
{
  "success": true,
  "data": {
    "length": 24,                        // 兼容旧字段：等于上限
    "minLength": 18,                     // v1.31.0 新增
    "maxLength": 24,                     // v1.31.0 新增（输入期按此截断）
    "hasRecovery": true,                 // 是否已设置
    "setAt": "2026-09-07T14:27:07.589Z",
    "lastUsedAt": null,
    "cooldownRemainingMs": 0             // 还需等待的毫秒数（0 = 立即可用）
  }
}
```

**只回显"是否已设置"与时间戳，绝不回显找回码本身**（因为库里只有哈希，物理上无法回显）。`minLength` / `maxLength` 供前端渲染计数器与提示文案，避免把 18/24 硬编码在界面里。

### 13.2 POST `/api/auth/recovery` — 设置/重设

请求：`{ code: string, password: string }`

处理顺序：
1. `validateRecoveryCode(code)` 格式校验（**18~24 位、仅字母数字**）→ 非法则 400
2. `verifyPassword(password, record)` 校验当前密码 → 错误则 400 **「当前密码错误」**
3. `setRecoveryCode(user.id, code)` → 写入新哈希，**同时清空 `recoveryLastUsedAt`（解除冷却）**

> 要求"当前密码"的理由：设置找回码等同于新增一把可改密码的备用钥匙，属敏感操作，需二次验证。若攻击者已拿到会话但不知道密码，也无法悄悄植入自己的找回码。

### 13.3 DELETE `/api/auth/recovery` — 清除

直接删除四个 recovery 字段。清除后立即失效，用旧码重置会返回 401。

### 13.4 POST `/api/auth/reset-by-recovery` — 重置密码（公开）

请求：`{ username, code, newPassword }`

```
1. validateRecoveryCode(code)           → 400（格式问题，与账号无关，可明确提示）
                                          注：18~24 位、仅字母数字；字符判定在长度之前
2. newPassword.length >= 6              → 400「新密码至少 6 位」
3. getUserByUsername(username)          ┐ 任一不满足 → 401「用户名或找回码错误」
   + verifyRecoveryCode(code, record)   ┘   （统一文案，不泄露用户名是否存在；含大小写回退）
4. recoveryCooldownRemainingMs(record)  → 429 + code: "RECOVERY_COOLDOWN"
5. updateUserPassword(...) + markRecoveryCodeUsed(...) → 200
```

**关键点**

- **统一错误文案**：步骤 3 无论"用户名不存在"还是"找回码错误"，都返回 `401 用户名或找回码错误`，避免通过响应差异枚举用户名。
- **限流在校验之后**：只有码正确才消耗冷却，攻击者无法通过错误尝试把合法用户"锁死"（否则就是可被利用的 DoS）。
- **限流响应**：

```jsonc
// 429
{
  "success": false,
  "error": "找回码使用过于频繁，请 537 秒后再试",
  "code": "RECOVERY_COOLDOWN"
}
```

## 14. 找回码前端实现

### 14.1 共用逻辑 `src/lib/recovery-code.ts`

单一事实来源，三个入口复用，避免规则散落：

```ts
// src/lib/recovery-code.ts（v1.31.0）
export const RECOVERY_MIN_LENGTH = 18;
export const RECOVERY_MAX_LENGTH = 24;

const ALNUM_RE = /^[A-Za-z0-9]+$/;

/** 清洗输入：剔除非字母数字（保留原大小写）、截断到上限位 */
export function sanitizeRecoveryInput(v: string): string {
  return (v || "").replace(/[^A-Za-z0-9]/g, "").slice(0, RECOVERY_MAX_LENGTH);
}

/** 校验（入参应为已清洗值）。合法返回 null，文案与后端逐字一致 */
export function validateRecoveryCode(v: string): string | null {
  const c = sanitizeRecoveryInput(v);
  if (!c) return "请输入找回码";
  if (!ALNUM_RE.test(c)) return "找回码仅支持字母和数字";
  if (c.length < RECOVERY_MIN_LENGTH || c.length > RECOVERY_MAX_LENGTH) {
    return `找回码需 ${RECOVERY_MIN_LENGTH}~${RECOVERY_MAX_LENGTH} 位`;
  }
  return null;
}
```

> 前端校验只是**体验优化**（即时提示 + `n/24` 计数），**服务端永远独立再校验一次**，不信任客户端。
> **改规则必须前后端同改** —— 两处实现不同步会出现「前端放行、后端 400」的诡异现象。

### 14.2 四个入口

| 入口 | 位置 | 行为 |
|---|---|---|
| **① 首次部署向导** | `SetupWizard.tsx`（`mode="create"`） | 「密码找回码」**可选**字段，留空可稍后补设；带 `n/24` 实时计数 |
| **② 账号重新设置** | `SetupWizard.tsx`（`mode="reinit"`） | v1.31.0 新增：老凭据版本账号登录后强制进入；用户名预填、**找回码必填**（见第三部分） |
| **③ 登录页** | `LoginPage.tsx` | 底部「忘记密码？」→ `RecoveryForm`（用户名 + 找回码 + 新密码 + 确认）→ 成功后返回登录并**预填用户名**；提示「找回码区分大小写，请按设置时的原始大小写输入」 |
| **④ 系统设置** | `Settings.tsx → 用户 → 密码找回码` | 状态徽章（已设置/未设置）+ 设置/上次使用时间 + 重设（需当前密码）+ 清除（`ConfirmDialog` 二次确认） |

输入框均挂 `onChange={(v) => setCode(sanitizeRecoveryInput(v))}`，配 `font-mono tracking-wider` 等宽字体便于核对。

## 15. 安全设计汇总（登录 + 找回）

| 威胁 | 对策 |
|---|---|
| 数据库泄露 → 直接拿到密码/找回码 | scrypt 哈希存储，明文不落盘 |
| 时序攻击 | `crypto.timingSafeEqual` 常量时间比较 |
| 彩虹表 | 每账号 / 每码独立 16B 随机 salt |
| 用户名枚举 | 登录「用户名或密码错误」、重置「用户名或找回码错误」统一文案 |
| XSS 窃取会话 | Cookie `httpOnly`，JS 读不到 |
| CSRF | Cookie `sameSite=lax` |
| 会话长期有效 | TTL 默认 30 分钟，用户可调 |
| 终端被未授权连接 | WS 握手独立校验会话，失败 `close(1008)` |
| 找回码泄露后被高频利用 | 10 分钟使用间隔限流（429） |
| 会话被劫持者偷偷植入找回码 | 设置/重设需校验当前密码 |
| 前端校验被绕过 | 服务端独立再校验，不信任客户端输入 |
| 未鉴权后门 | 全局 `/api` 守卫；`/auth/*` 豁免区内的敏感路由逐个显式挂 `requireAuth` |
| **任何人夺取管理员账号** | `POST /api/auth/reinit` **必须 `requireAuth`** —— 先证明持有旧凭据才允许覆盖账号 |
| **改密后旧会话仍可用** | reinit / 改密成功后 `destroySessionsForUser(userId)` 作废该用户**全部会话**，并连当前会话一并销毁 |
| **老记录因规则变更失效** | `legacyUpperVariants()` 多候选回退（只加候选、不改规则，新记录敏感度不受影响） |
| **凭据规则随版本漂移导致旧库不适用** | `credentialVersion` 显式版本号 + 登录后强制重走初始化，规则变更不再依赖「静默兼容」 |

## 16. 完整流程

```
【初始化】无账号 → 向导：用户名 + 密码 + (找回码)
        → POST /api/auth/init → 建号 + 下发会话 → 主应用

【升级（老凭据版本）】OTA 换包重启 → init-status.needsReinit = true
        → 未登录：登录页 → 输入【旧】用户名 + 密码（旧凭据仍可用）
        → 已登录：App 直接切 reinit
        → SetupWizard(mode="reinit")：用户名（预填）+ 新密码 + 找回码（必填）
        → POST /api/auth/reinit → 覆盖凭据 + 写 credentialVersion=2
        → 作废【全部】会话 → 回登录页（绿色提示「账号已重新设置」）
        → 用【新】凭据登录 → 主应用
        ※ 期间任何业务接口均返回 403 REINIT_REQUIRED

【登录】LoginPage → POST /api/auth/login → Set-Cookie(httpOnly) → 主应用
        会话失效/重启 → 任意接口 401 → auth:unauthorized → 回登录页

【设置找回码】已登录 → 系统设置 → 用户 → 密码找回码
        输入新码（18~24 位，区分大小写）+ 当前密码 → POST /api/auth/recovery
        → 服务端校验格式 + 当前密码 → scrypt 哈希写库 → 200

【找回】未登录 → 登录页 → 忘记密码
        输入用户名 + 找回码 + 新密码（≥6 位）×2 → POST /api/auth/reset-by-recovery
        → 格式校验 → 用户查找 + 哈希比对（含老记录大写回退）→ 冷却检查
        → 更新密码 + 记录使用时间 → 200
        → 前端提示「密码已重置」→ 返回登录（预填用户名）

【清除】系统设置 → 用户 → 密码找回码 → 清除 → ConfirmDialog 确认
        → DELETE /api/auth/recovery → 删除全部 recovery 字段 → 旧码立即失效
```

# 第三部分：账号重新初始化（凭证版本升级）

> v1.31.0 起生效。触发场景：**OTA 升级后，老库的凭据规则与新版本不兼容**。

---

## 19. 背景：为什么要强制重走一次

v1.31.0 同时改了三件事：用户名由用户重定、密码重设、找回码规则从「24 位 + 忽略大小写」变为「18~24 位 + 区分大小写」。老 `users.json` 里既没有「这份凭据是按哪版规则生成的」标记，也无法从哈希反推原始找回码 —— 于是出现三个必须回答的问题：

| 问题 | 若不处理的后果 |
|---|---|
| 这份凭据是不是按当前规则生成的？ | 无从判断，只能靠猜，规则每变一次都要写一段「静默兼容」代码 |
| 老找回码还能用吗？ | 大小写语义变了 ⇒ 静默兼容只能做「多试一次大写」，混合大小写输入仍失效 |
| 用户愿不愿意重设？ | 不知道，于是永远不敢改规则 |

**结论：把"版本"显式写进数据里，并在不匹配时让用户自己完成一次重设** —— 用一次性的操作成本，换掉长期累积的兼容分支。

**实现要点**

- `UserRecord.credentialVersion?: number` + 常量 `CREDENTIAL_VERSION = 2`。
- `needsReinit(record)`：`(record.credentialVersion ?? 1) < CREDENTIAL_VERSION`。
  - **缺字段视为 1**（老库无此字段）⇒ 自然判为需要重设，无需额外迁移脚本。
- `requiresAccountReinit()`：只要**存在任一**待重设账号即为真（当前为单管理员，等价于判断那一个账号）。
- `createUser` / `reinitUser` 均写入 `CREDENTIAL_VERSION`。

> **为什么不做自动迁移**：密码可以重算哈希（用户明说新密码），但**找回码不行** —— 库里只有 scrypt 哈希与 salt，物理上无法还原明文，也就无法按新规则重新哈希。既然找回码无论如何都要用户手输一次，不如把「用户名 + 密码 + 找回码」一并在同一次引导里收齐。

## 20. 服务端实现

### 20.1 拦截层（顺序敏感）

见 **§5.1**。核心是三层判定：

```
requiresAccountReinit() === false        → 直接放行（老库升级后不误伤、全新安装不介入）
req.path ∈ REINIT_ALLOWED_AUTH           → 放行（否则密码忘 + 待重设 = 双锁死）
其余                                     → 403 { code: "REINIT_REQUIRED" }
```

> ⚠️ 该中间件**紧跟 `cors()` / `express.json()`**，且**必须早于所有 `/api/auth/*` 路由注册**。

### 20.2 `POST /api/auth/reinit`

见 **§7.4**。关键点三条：

1. **`requireAuth`** —— 先证明持有旧凭据，才允许覆盖账号（否则等于开放接管通道）。
2. **`reinitUser` 不校验旧密码** —— 因为用户可能正是因为「旧密码记不清了」才用找回码登录进来重设；要求再输一次旧密码会把这条路径堵死。安全性由「已持有有效会话」+「持有旧凭据中的任意一种」共同保证。
3. **成功后作废该用户全部会话**（`destroySessionsForUser` + `destroySession`）—— 否则改写密码后旧会话仍可用，改密的意义被削弱。

### 20.3 数据落盘

`reinitUser()` 的写入策略：

| 字段 | 动作 |
|---|---|
| `id`、`createdAt` | **保留**（账号身份与创建时间不变，备份/审计可对齐） |
| `username`、`usernameKey` | 覆盖（同时刷新小写唯一键） |
| `passwordHash`、`salt` | 重新生成 salt + scrypt 哈希 |
| `recoveryHash`、`recoverySalt`、`recoverySetAt` | 覆盖为新码 |
| `recoveryLastUsedAt` | **清空**（重设即解除 10 分钟限流） |
| `credentialVersion` | 写为 `2`；`credentialUpdatedAt` 记当前时间 |

全部字段先组装再**一次性落盘**（`saveUsers`），中途不写文件，避免半更新状态。

## 21. 前端实现

### 21.1 状态机

`authState: "loading" | "setup" | "login" | "reinit" | "authed"`，完整判定逻辑与迁移规则见 **§6**。

两条触发路径，必须都覆盖：

| 场景 | 触发点 |
|---|---|
| 升级后**未登录**打开页面 | 启动检测读 `init.needsReinit` → `login` → 登录成功后按 `user.needsReinit` 转 `reinit` |
| 升级后**已登录**（页面开着，后端换了包） | 启动检测 `init.needsReinit` + `meRes` 存在 → 直接 `reinit`；或运行中撞 `403 REINIT_REQUIRED` → `auth:reinit-required` 事件 → `reinit` |

### 21.2 表单与提示

- `SetupWizard` 复用同一套字段与校验，仅标题 / 提示条 / 找回码必填性 / 提交接口不同（见 §8）。
- reinit 提交成功后**不能直接进主应用**：服务端已作废全部会话，此时没有任何有效会话，必须回登录页。
- 回登录页时带 `notice` 绿色提示条「账号已重新设置，请使用新的用户名和密码登录」，避免用户以为被登出是故障。
- 登录页的 `notice` 在登出、重新发起登录时清除（`setLoginNotice(undefined)`），不残留过期提示。

### 21.3 与「忘记密码」的关系

三条自救路径的分工（务必区分）：

```
还记得旧密码       → 登录 → 被引导到 reinit → 输入新用户名/密码/找回码
不记得旧密码、有旧找回码 → 登录页「忘记密码」→ reset-by-recovery → 回登录 → 再走 reinit
两者都没有         → 无自动通道；需直接改库或重装（见 §18）
```

> 第二条路径能成立的前提是 **`reset-by-recovery` 在白名单里**（§5.1）—— 这是本次实现里最容易漏掉、后果最严重的一处：漏了就等于把这类用户彻底锁死。
